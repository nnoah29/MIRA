# Règles « condition → action » — plan d'implémentation

> **Pour les agents :** sous-compétence requise : `superpowers:subagent-driven-development` (recommandé) ou `superpowers:executing-plans`. Les étapes utilisent des cases `- [ ]`.

**Objectif :** exécuter automatiquement des règles (conditions combinées en « OU de groupes ET », actions ordonnées) sur les nouveaux messages, éditables depuis l'app.

**Architecture :** types dans `mira-vocabulary` ; module `rules` (évaluateur pur, validation) et dépôt SQLite dans `mira-core` ; accroche dans `announce_batch` de la synchro, actions soumises par `actions::submit` ; nouveau domaine `rule` du contrat ; l'app passe par le pont générique JSON.

**Stack :** Rust 1.99 (édition 2024), `serde`, `rusqlite`, crate `regex` (à ajouter à `mira-core`), Flutter/Dart.

**Spec :** `docs/specs/R1-regles.md`

## Contraintes globales

- Normes `tools/check-norms` : fonction ≤ 30 lignes ; fichier ≤ 6 fonctions avec corps (tests compris) ; aucun commentaire dans un corps de fonction ; une seule ligne `///` en français avant chaque `fn` ; `//!` de 1 à 3 lignes en tête de fichier ; interdits : `utils.rs`, `helpers.rs`, `common.rs`, `misc.rs` ; tests dans des fichiers séparés (`crates/mira-core/tests/`).
- Pas de `unsafe`, pas de `unwrap`/`expect`/`panic!` hors tests, aucun secret dans journaux, erreurs ni événements.
- Le cœur ne nomme aucun provider ; `mira-vocabulary` ne dépend que de `serde` et `thiserror`.
- JSON étiqueté `type`, `snake_case` (comme `ActionKind`) ; règles = configuration, migrées sans perte.
- Règles exécutées uniquement pour `Ingested::Created` en `Announce::Live`, jamais en `Announce::Silent`.
- Boîtes exclues de l'évaluation : rôles Envoyés, Brouillons, Corbeille, Spam.
- Précision sur la spec §3 : la portée est stockée avec une colonne `scope_all` (booléen) en plus de `rule_accounts`, pour qu'une règle dont le dernier compte est supprimé ne devienne pas une règle « tous les comptes » (elle devient invalide : portée vide).
- Ne pas lancer `./ci.sh` sans l'accord explicite de l'utilisateur : vérifier avec `cargo test -p <crate> --test <fichier>`, `cargo clippy` et `cargo fmt` ciblés.
- Commits au nom de l'utilisateur, sans trailer d'attribution. Branche de travail : `feat/regles` (depuis `dev`).

## Points d'attention (Review Focus)

1. Règle visant un compte unique dont le compte est supprimé : portée vide ⇒ règle invalide et non exécutée, jamais « tous les comptes ».
2. Expression régulière pathologique ou énorme : refusée à l'enregistrement (taille plafonnée), jamais de blocage de la synchro.
3. Message sans expéditeur, sans objet ou sans aperçu : une condition positive est fausse, sa négation est vraie, sans erreur.
4. Casse et accents : la comparaison ignore la casse Unicode (`É` = `é`), y compris pour `in_list`.
5. Même message présent dans plusieurs boîtes (vues Gmail) : évalué une seule fois ; message arrivé dans Envoyés/Spam/Corbeille : non évalué.
