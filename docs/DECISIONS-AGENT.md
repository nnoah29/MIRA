# Décisions prises par l'agent

Format : **AG-xx — titre** · contexte · options · choix · raison · retour arrière.

## AG-01 — Garde-fous écrits en Python 3 (bibliothèque standard)
- **Contexte** : `tools/check-norms` et `tools/check-architecture` doivent analyser le code Rust et `cargo metadata`.
- **Options** : crate Rust (avec `syn`) dans le workspace, ou script Python sans dépendance.
- **Choix** : Python 3, bibliothèque standard seulement.
- **Raison** : pas de nouvelle dépendance Rust ; l'outil n'est pas du code du moteur et n'est donc pas soumis à ses normes ; `python3` est présent ; un lexer maison suffit (chaînes, caractères, commentaires, accolades).
- **Retour arrière** : réécrire l'outil en crate Rust ; l'interface (code de sortie, format des messages) reste la même.

## AG-02 — Sous-agents lancés en `general-purpose` avec fichier de rôle
- **Contexte** : les rôles écrits dans `.claude/agents/` pendant la session ne sont pas chargés par l'outil Agent (types introuvables).
- **Choix** : lancer `general-purpose` (modèle sonnet pour implémenteurs et testkit, opus pour relecteur et qualité), en demandant de lire d'abord `.claude/agents/<rôle>.md`, et en interdisant explicitement les outils web dans la consigne des rôles qui n'y ont pas droit.
- **Raison** : seul moyen de déléguer sans redémarrer la session. Les définitions restent valables pour une session future.
- **Retour arrière** : relancer Claude Code ; les types `implementeur-rust`, etc. seront alors disponibles.

## AG-03 — Connexion en clair autorisée seulement vers la boucle locale
- **Contexte** : le testkit écoute en clair sur 127.0.0.1 ; la production exige TLS.
- **Choix** : `Security::Plaintext` existe dans le vocabulaire, mais le cœur refuse (`tls.plaintext_refused`) toute connexion en clair vers un hôte qui n'est pas `127.0.0.1`, `::1` ou `localhost`.
- **Raison** : tester le vrai client IMAP/SMTP contre de faux serveurs sans certificats, sans jamais affaiblir la production.
- **Retour arrière** : ajouter des certificats de test (crate `rcgen`) et supprimer la variante.

## AG-04 — Contrat d'API : énumérations `Request`/`Response` et un handler par opération
- **Contexte** : §11.8 du brief (un handler par opération, routage par `match` exhaustif) et D-30 (même contrat en processus ou séparé).
- **Choix** : `Engine::execute(Request) -> Result<Response, MiraError>` ; chaque variante est routée vers son propre fichier de handler. Les énumérations sont sérialisables (même forme pour CLI `--json`, Flutter, ou un futur transport).
- **Raison** : contrat testable par instantané JSON, invariant 6 vérifiable par énumération.
- **Retour arrière** : ajouter des méthodes typées au-dessus ; les handlers restent.

## AG-05 — Stockage : `Database` + transaction `Tx`, dépôts en blocs `impl Tx`
- **Contexte** : aucune fuite de `rusqlite` hors de `storage/` (annexe H) ; écritures atomiques composées par la synchro.
- **Choix** : `Database { Mutex<Connection> }`, `write(|tx| …)` / `read(|tx| …)` ; un fichier par opération ou groupe d'opérations d'une entité. Accès synchrone depuis le code async (requêtes courtes, un seul écrivain).
- **Raison** : simplicité et lisibilité pour un développeur C++ ; un seul écrivain cohérent avec le verrou de profil (D-27).
- **Retour arrière** : déplacer les appels dans `spawn_blocking` ou un fil dédié derrière la même API.

## AG-06 — Le client IMAP réel est testé contre le faux serveur, sans maquette du client
- **Contexte** : P10 (testable sans réseau) et annexe H (remplaçable par un faux).
- **Choix** : le faux est côté serveur (testkit sur 127.0.0.1). Le client IMAP/SMTP du moteur est un type concret encapsulé, testé de bout en bout contre le testkit.
- **Raison** : on teste le vrai code de protocole ; pas de trait asynchrone dynamique compliqué.
- **Retour arrière** : extraire un trait `MailBackend` (6.10) le jour où un second backend arrive.

## AG-07 — `cargo deny` sans la vérification des avis de sécurité
- **Contexte** : `cargo deny check advisories` télécharge la base d'avis depuis GitHub (réseau hors crates.io, règle 2).
- **Choix** : `./ci.sh` exécute `cargo deny check bans licenses sources` seulement.
- **Retour arrière** : ajouter `advisories` quand le réseau est autorisé.

## AG-08 — Écarts acceptés du vocabulaire (rapport J1)
- `MiraError.context` est un `Box<ErrorContext>` (clippy `result_large_err`) ; JSON inchangé.
- Marqueurs d'identifiants nommés `AccountMarker`… (évite le conflit avec `ActionKind`).
- `Timestamp` et `Id<K>` sérialisés de façon transparente (entier, chaîne).
- `EmailAddress` désérialisée avec validation ; espaces refusés dans la partie locale.
- `EventKind::category()` et `account()` en `#[rustfmt::skip]` pour tenir en 30 lignes (match exhaustif de 44 variantes).
- `EventFilter` : un filtre par compte exclut les événements sans compte ; `after` strict.
- **Temporaire** : `storage::json_columns` porte `#[allow(dead_code)]` jusqu'à son premier usage par les dépôts J2 (à retirer à la fusion de J2).

## AG-09 — Comportements des faux SMTP et OAuth (rapport J4 partie B)
- SMTP : `MAIL FROM` avant `AUTH` → `530` (comme un serveur de soumission réel) ; `fail_next` est une file FIFO ; une panne en fin de DATA n'enregistre pas le message ; `drop_after_data_once` enregistre puis coupe sans répondre.
- OAuth : `approve`/`deny` refusent toute requête invalide et tout `redirect_uri` qui n'est pas en boucle locale ; code à usage unique consommé même si le vérificateur est faux ; le rafraîchissement ne renouvelle pas le jeton de rafraîchissement ; jetons générés par compteur, jamais journalisés.
- Modules `oauth::pkce` et `oauth::form` publics (fonctions pures testées).

## AG-10 — Comportements du faux IMAP (rapport J4 partie A)
- Un seul commit pour tout le serveur (niveaux interdépendants).
- `connection_count()` = total des connexions acceptées ; `active_connections()` = connexions ouvertes (à utiliser pour l'invariant 25).
- QRESYNC exige `ENABLE QRESYNC` avant SELECT (sinon `BAD`), comme un serveur réel ; MODSEQ n'apparaît dans les FETCH qu'une fois CONDSTORE activé.
- `renumber` redémarre les UID à 1 et change UIDVALIDITY ; `deliver_dated` permet des dates internes contrôlées (fenêtre de 90 jours).
- `X-GM-LABELS` : noms des boîtes contenant le message (`INBOX` → `\Inbox`, boîtes `\All` exclues).
- Non supportés : BODYSTRUCTURE, sections numérotées, LSUB, UNSELECT, NAMESPACE, STARTTLS, X-GM-RAW.

## AG-19 — CLI sur la façade (rapport J9a)

## AG-20 — Rejeu, envoi, reprise (rapport J7c)
- `Message-ID` d'envoi dans `ServerTargets.sent_message_id` (serde default, sans migration) ; un envoi relancé par l'utilisateur reçoit un nouveau `Message-ID`.
- Le rejeu s'arrête au premier échec passager ou d'authentification (ordre, inv. 19) ; définitif ou succès : on continue.
- Classement : `Authentication` et `secrets.secret_missing` → auth ; `Network/Tls/LocalStorage/Internal/Cancelled/Secrets` et `Server` retryable → passager ; le reste → définitif.
- Après acceptation SMTP aucune erreur ne remonte (copie Envoyés, événements, suppression du brouillon : `tracing::warn`) : jamais de renvoi pour un échec secondaire.
- Coupure `network.connection_lost` après DATA → vérification immédiate dans Envoyés (Uncertain ou Succeeded). Reprise : Envoyés illisible → reste `InProgress`.
- Copie Envoyés sans Bcc ; `SaveDraft` sans destinataire = sans effet.
- **À faire (J8)** : `Engine::open` construit un `ReplayContext` par compte, appelle `recover_interrupted_actions` puis `replay_actions` ; implémentation de production de `ReplayCredentials` au-dessus de `CredentialVault`.

## AG-24 — CLI lecture/écriture (rapport J9b)
- Un CLI vit le temps d'une commande : les opérations longues (`message fetch`, `save-attachment`, `search server`) sont toujours attendues (`--timeout`, 120 s) ; les actions de file seulement avec `--wait` (60 s) sur `action apply`, `mailbox create|rename|delete|empty`, `draft send|resolve-send`, `queue retry`. Action Failed → code 16 ; Uncertain ou délai → 13 (l'action reste en file).
- `search server-result` exposé pour le contrat mais ne retrouve rien d'un autre processus (code 11).
- Instants : ms Unix, `AAAA-MM-JJ` ou `AAAA-MM-JJTHH:MM[:SS][Z]`, UTC. Destinataires `adresse` ou `Nom <adresse>` ; valeur vide efface ; `--body-file`.
- `mailbox set-synced` : boîtes en arguments positionnels, boîte inconnue → code 10.
- Dépendance `base64` ajoutée à mira-cli.

## AG-25 — Façade Synchro et cycle de vie (rapport J8d)
- `BackgroundSync { Off, On(SupervisorConfig) }` dans `NetworkPolicy` : Off par défaut (tests), On dans `production_config`. Sans runtime tokio, synchro désactivée ; `StartSync`/`ExtendWindow`/`ResyncMailbox` → `incompatible_state.sync_disabled`.
- `Engine::shutdown` synchrone (abort) ; `Engine::shutdown_within(deadline)` async pour l'arrêt propre ; `Drop` interrompt les tâches.
- `PauseSync` = pause du compte ; `StartSync` sur compte en pause → `incompatible_state.account_paused`. `AddAccount` lance la première synchro ; une suppression de compte interrompue est achevée à l'ouverture (`accounts/deletion.rs`).
- Une demande de synchro (Account / Mailbox / Resync) est servie par la tâche du compte par une passe démarrant après elle (inv. 24).
- Secret absent pendant la synchro → `authentication.rejected` (AuthRequired).
- Limite héritée : un message arrivé entre la fin de la première passe et l'établissement d'IDLE n'est vu qu'au relevé suivant (correctif possible : passe de la réception juste après le démarrage d'IDLE).
- **À faire (J9c)** : CLI `sync`, politique `BackgroundSync` par commande (Off hors synchro, On pour `sync start --wait`).

## AG-26 — CLI Synchro, politique de synchro de fond, OAuth en un processus (rapport J9c)
- `execute_request` fixe `background_sync` par commande : `On` seulement pour `sync start|extend-window|resync` et `account add|add-oauth --sync-wait` ; `Off` ailleurs. Arrêt par `shutdown_within(5 s)` quand la synchro tournait.
- `sync start --wait` accepté sans effet (le CLI attend toujours : un processus qui rend la main tue la synchro).
- `Engine::open` avec synchro `On` lance une passe pour chaque compte connu : `sync start --mailbox X` synchronise aussi les autres boîtes (comportement du cœur).
- `mira account add-oauth` : StartOAuth, URL sur stderr, CompleteOAuth borné (`--timeout` 300 s, code 13 et CancelOAuth au délai), puis AddAccount.
- Le `warn!` « première synchro non lancée » d'`AddAccount` est masqué par une directive par défaut du CLI : à supprimer côté moteur quand la synchro est `Off`.
- **Reste** : API moteur pour attendre la première synchro lancée par `AddAccount`.

## AG-28 — Corrections du lot B (synchro, budget, lecteur IMAP, suppression)
- Un `ConnectionBudget` par compte, tenu par le moteur (`ConnectionBudgets`, clé = identifiant du compte ; `candidate:<adresse>` pour un test avant ajout), pris avant tout `ImapClient::connect` (rejeu, téléchargements, recherche serveur, tests de connexion, synchro, extension de plage). `ImapAccess::connect` rend un `LeasedClient` ; au plus 16 demandes explicites en attente par compte (`server.rate_limited`).
- Téléchargement à la demande : ignore les apparitions à revalider, compare `uid_validity`, exige le même Message-ID (sinon `not_found.message`).
- Orphelins : recoupement contre l'orphelin unique de la passe (sans jumeau vivant) ; pas de purge si une boîte a été ignorée. **Limite** : boîte de destination traitée avant la source (désarchivage vers la réception) crée encore un nouveau message — fusion en fin de passe non faite.
- Déplacement : « déjà arrivé » = même Message-ID + même taille + date interne à ±60 s ; Message-ID en plusieurs exemplaires sans UID fiable = ambigu, rien n'est touché. **Limite** : deux copies identiques à ±60 s sont tenues pour la même (fermer en persistant « tentative commencée »).
- Lecteur IMAP : ligne 1 Mo, littéral 64 Mo, réponse 64 Mo, allocation progressive, délai d'inactivité réarmé par bloc ; dépassement = connexion `broken`.
- Préchargement : échec Server d'un message journalisé et ignoré ; pas de préchargement > 10 Mo.
- VANISHED > 1 M d'UID ou avec `*` → repli sur la comparaison complète ; dates internes bornées 1900–9999, `checked_*`.
- Rétention des événements : 30 jours ou 100 000 lignes, à l'ouverture et après chaque passe ; opérations : 256 terminées conservées.
- S14 : suppression des fichiers de cache de pièces jointes, attente de la passe de rejeu (30 s, verrou par compte `replayer/gates.rs`) ; `extend_window` refuse si l'UIDVALIDITY a changé (`incompatible_state.mailbox_changed`) ; la synchro respecte `NetworkPolicy`.
- Non traité : `extend_window` s'exécute encore en parallèle de la tâche du compte ; attente du rejeu sans test déterministe ; repli VANISHED sans test d'intégration.

## AG-30 — Lot D : un envoi dont l'issue est inconnue n'est jamais renvoyé
- Pour une action `Send`, toute erreur réseau autre que `network.unreachable` est « issue inconnue » → `settle_interrupted_send` (Message-ID cherché dans Envoyés : `Succeeded` ou `Uncertain`). `network.timeout` n'est plus produit par le client SMTP : échec de connexion TCP (délai compris) = `network.unreachable` (passager) ; panne dans la session = `network.connection_lost`. **Corrige AG-27** sur ce point.
- Toute future erreur réseau passagère d'un envoi doit être normalisée en `network.unreachable` avant `settle_failure` (fait pour le rafraîchissement de jeton).
- La copie serveur du brouillon est aussi purgée quand l'envoi est retrouvé dans Envoyés à la reprise (échec seulement journalisé).

## AG-35 — Identifiants OAuth lus dans un fichier de configuration TOML
- **Contexte** : `production_config` construisait un `OAuthClientConfig` vide, donc `account add-oauth` était inutilisable en production. Choix de l'utilisateur : un fichier de configuration (pas de variables d'environnement).
- **Choix** : `mira-assembly` lit `$MIRA_CONFIG`, sinon `$XDG_CONFIG_HOME/mira/config.toml` (absolu), sinon `~/.config/mira/config.toml`. Format `[oauth.<provider>] client_id = "…"` ; champ inconnu dans une entrée et `client_id` vide refusés. Fichier absent = configuration vide ; fichier illisible = `tracing::warn!` puis configuration vide (`production_config` reste infaillible). `production_config_with_oauth` permet d'imposer la configuration (tests hermétiques). Dépendances ajoutées : `toml` (features `parse`, `serde`), `tracing` et `serde` dans `mira-assembly`.
- **Raison** : l'identifiant dépend de l'installation, pas du provider (providers purs, P10) ; seul l'assemblage lit l'environnement. Les noms de providers du fichier ne sont pas validés contre le registre (une faute de frappe donne le code 10).
- **Retour arrière** : retirer les trois modules `oauth_file_*` et rétablir `OAuthClientConfig::default()` dans `production_config`.

## AG-36 — `client_secret` OAuth facultatif
- **Contexte** : AG-35 ne gérait que `client_id`. Un client OAuth « application de bureau » peut devoir présenter un `client_secret` à l'échange du code et au rafraîchissement (à vérifier auprès du service ; non vérifié en ligne ici).
- **Choix** : `OAuthClientConfig.client_secrets` (`SecretValue`, `Debug` masqué), clé `client_secret` facultative de `[oauth.<provider>]`. Nouvelles variantes `exchange_code_with_secret`, `refresh_tokens_with_secret`, `refresh_access_token[_if_stale]_with_secret` ; les anciennes fonctions délèguent avec `None` (clients publics, tests inchangés). `PendingFlow::set_client_secret`. Le faux serveur OAuth sait exiger un secret (`require_client_secret`, 401 `invalid_client`).
- **Fuite évitée** : le message d'erreur de `toml` cite la valeur fautive ; les erreurs de lecture ne donnent plus que la ligne (test `empty_secret_refused_and_value_never_printed`).
- **Limite** : le secret est en clair dans `config.toml` (`chmod 600` recommandé) ; MIRA ne vérifie pas les permissions du fichier. Ce n'est pas le trousseau : il s'agit d'un secret d'application, pas d'un secret de compte.
- **Retour arrière** : retirer `client_secrets` et les variantes `_with_secret`.

## AG-37 — Actions du TUI : corbeille sans confirmation, nonce de session
- **Contexte** : le TUI envoie des actions sur les messages (archiver, corbeille, suppression définitive, étoile, lu, déplacement). Le moteur dédoublonne par clé d'idempotence : des clés fixes réutilisées d'un lancement à l'autre feraient prendre de vraies actions pour des doublons.
- **Choix** : seule `DeletePermanently` exige une confirmation modale ; `Trash` part sans confirmation (réversible par `z`). Le constructeur `AppState::new(width, height, nonce)` exige un nonce de session (sans valeur par défaut), repris dans toutes les clés : `tui-<nonce>-act-<n>`, `tui-<nonce>-read-<id>-<n>`. À l'échec de la dernière action, l'erreur est affichée et la vue courante rechargée ; `z` n'annule que l'action confirmée la plus récente (rien tant qu'une action est en vol), et une annulation échouée restaure l'action pour réessayer.
- **Raison** : la corbeille se défait ; la suppression définitive non. Le nonce garantit l'unicité des clés entre sessions, le compteur au sein d'une session.
- **Retour arrière** : demander la confirmation aussi pour `Trash` (ajouter une variante de `Popup`) ; le nonce ne se retire pas sans risque de collision de clés.

## AG-38 — Boucle et clavier du TUI : taille relue à chaque tour, `]`/`[`, Ctrl+c, recherche non paginée
- **Contexte** : `run_loop` reçoit seulement des `KeyEvent` (signature imposée) ; la spec (§4.2) demande que le redimensionnement soit pris en compte à chaque tour sans état caché. Le changement de compte et l'interruption n'ont pas de touche dans la spec §4.3. La recherche du moteur est paginée (50 par page).
- **Choix** : le fil d'entrée (`crossterm::event::{poll, read}`) n'envoie que les touches ; la boucle relit `terminal.size()` à chaque tour (battement de 200 ms) et émet `Msg::Resize` si elle a changé. `]`/`[` changent de compte dans la barre latérale ; Ctrl+c quitte partout (y compris en saisie et sous une fenêtre). Les résultats de recherche ne sont pas paginés : seule la première page est montrée et le titre l'indique (« N premiers résultats ») quand le moteur annonce une page suivante. À la sortie, la boucle attend au plus 3 s les requêtes en vol puis interrompt les dernières, pour que `close_engine` trouve le moteur non partagé.
- **Raison** : solution la plus simple compatible avec la signature ; aucune touche existante n'est détournée.
- **Retour arrière** : faire porter au canal un `enum` touche/redimensionnement ; paginer la recherche comme la liste (`Tag::Search` avec curseur).

## AG-39 — TUI : terminal rendu avant la fermeture du moteur, signaux et paniques
- **Contexte** : la spec du TUI (§5) demande l'arrêt propre du moteur (`shutdown_within`) avant de rendre le terminal. Cet arrêt peut durer plusieurs secondes (synchros de fond), pendant lesquelles l'écran resterait figé. Un signal extérieur (SIGTERM, SIGINT, SIGHUP) ou la panique d'une tâche de fond ne doivent ni laisser le terminal en mode brut, ni casser l'affichage, ni bloquer l'état.
- **Choix** : écart assumé à la spec : la boucle se termine, le terminal est rendu (garde détruit), « Fermeture de MIRA… » est écrit sur stderr (écran normal), puis le moteur est fermé (`app::session::run_session_parts`). SIGTERM/SIGINT/SIGHUP passent par `tokio::signal` (feature `signal` du crate `mira-tui`) et prennent le même chemin de sortie que `q`. Le crochet de panique ne restaure le terminal que pour une panique du fil qui l'a installé (fil principal, qui détient le garde) ; la panique d'une tâche de requête devient une réponse `internal.bug` étiquetée, ce qui libère les marqueurs « en vol » et affiche l'erreur dans la barre d'état.
- **Complément (revue de l'étape 1)** : l'attente des requêtes encore en vol (au plus 3 s, AG-38) se fait elle aussi après la restauration et l'avis (`run_loop_detached`), juste avant `close_engine`.
- **Raison** : l'utilisateur retrouve son terminal immédiatement et sait que la fermeture est en cours ; aucun chemin de sortie connu ne laisse le terminal en mode brut.
- **Retour arrière** : dans `run_session_parts`, appeler `close_engine` avant `drop(guard)` et supprimer l'avis.

## AG-41 — TUI : pas de rejeu des événements d'avant la session
- **Contexte** : `Engine::subscribe(EventFilter::default())` repart du numéro 0 et rejoue tout le journal conservé : un message et un dessin par événement ancien, une relecture des comptes par `AccountAdded` ancien, un vieux `ActionFailed` affiché comme récent. Le contrat ne donne pas le dernier numéro d'événement.
- **Choix** : au démarrage, la tâche du flux lit le journal par pages de 1 000 (`EventRequest::GetEvents`) sans réagir, retient le dernier numéro, puis s'abonne avec `after` = ce numéro ; les événements survenus entre-temps sont rattrapés par l'abonnement. La boucle applique tous les messages déjà arrivés avant de redessiner (un dessin par rafale) ; `refresh.accounts` empêche d'empiler les relectures des comptes. Proposition PR-18 pour obtenir ce numéro en une requête.
- **Raison** : solution la plus simple sans modifier le moteur ; l'horodatage `event.at` dépend de l'horloge du moteur (manuelle en test) et n'est pas comparable à l'horloge du TUI.
- **Complément (re-revue)** : le dernier numéro est relevé AVANT d'envoyer les lectures de démarrage (`run_session` : `latest_event_seq`, puis `Runtime::start(engine, after)`, puis `boot_commands` + `refresh_status`) ; toute lecture de démarrage est donc postérieure au curseur et tout événement postérieur est livré (au pire un rechargement de plus). Le premier écran est dessiné avant le balayage. Si une page de `GetEvents` échoue, le balayage s'arrête au dernier numéro lu : le reste du journal est alors rejoué. C'est le choix le moins dangereux, car le pire cas est un affichage d'événements anciens (comportement d'avant AG-41), jamais une perte. Les messages déjà arrivés sont appliqués par rafales d'au plus 256 (`app::burst`), pour ne pas priver le clavier.
- **Retour arrière** : revenir à `spawn_event_feed` (abonnement depuis le début).

## AG-40 — TUI : défilement par fenêtre, mais liste chargée non bornée en mémoire
- **Contexte** : D-32 et la spec du TUI (§5) demandent de parcourir 100 000 messages sans tout charger. Le TUI redessinait chaque message chargé et re-neutralisait le corps entier à chaque image (toutes les 200 ms).
- **Choix** : la liste ne construit que les lignes visibles (`view::message_list::window`, fenêtre sans état autour de la sélection) ; le corps est neutralisé une seule fois à la réception (`on_body`) et seules les lignes visibles, à partir du défilement (en lignes du texte), sont repliées. Limite assumée : `MessagesState::append_items` garde toutes les pages déjà parcourues (≈ 100 000 résumés après un parcours complet) ; le rafraîchissement redemande au plus 500 messages (borne du moteur), et au-delà la sélection peut être recadrée par indice (l'action du lecteur vise toujours le message ouvert).
- **Raison** : le coût par image ne dépend plus de la taille de la liste ; borner la mémoire demande une fenêtre de pages avec éviction, reportée.
- **Retour arrière** : reconstruire toutes les lignes (`List` de ratatui avec tous les éléments) ; neutraliser à l'affichage.

## AG-42 — TUI : éditeur de brouillon (étape 2, tâche 10)
- **Contexte** : le moteur construit le brouillon (destinataires, objet, lien vers l'original) mais `CreateDraft` n'a pas de clé d'idempotence et `UpdateDraft` remplace des champs entiers. Le TUI doit éditer sans jamais envoyer d'adresse invalide, sans perdre de frappe et sans qu'un rechargement automatique ferme l'éditeur.
- **Choix** : (1) éditeur maison (`state::compose::TextBuffer`), curseur en indices de caractères ; un tampon par champ, texte de référence = texte du tampon juste après chargement (un `\r\n` du moteur n'est donc pas une modification). (2) `Ctrl+s` n'envoie que les champs dont le texte diffère de la référence ; une adresse invalide (analyse `Nom <a@b.c>`, `EmailAddress::parse`) est signalée sur le champ et écartée de l'envoi, les autres champs partent quand même ; la référence n'est mise à jour qu'à la confirmation du moteur et avec le texte réellement envoyé (ce qui est tapé pendant l'enregistrement reste à enregistrer). Un seul enregistrement en vol. (3) Un texte modifié efface la version HTML existante (`body_html: ""`). (4) Création suivie par un jeton (`Tag::DraftCreated(IdempotencyKey)`) : une seule création à la fois, la réponse d'une autre demande est ignorée. (5) Échap avec modifications ouvre une confirmation (enregistrer / abandonner / continuer) ; un brouillon que l'utilisateur n'a jamais enregistré est supprimé (`DeleteDraft`) à la fermeture, pour ne pas laisser un brouillon pré-rempli par `r` à chaque aperçu ; un brouillon enregistré au moins une fois est toujours gardé. (6) Pendant l'édition toute touche imprimable est du texte (Ctrl/Alt non, AltGr oui) ; Ctrl+c quitte quand même sans enregistrer (comme partout, AG-38). (7) Le texte des champs n'atteint le terminal qu'après `display_safe`, fenêtré autour du curseur (colonnes d'affichage via `Span::width`, sans dépendance de plus).
- **Complément (revue, correction 1/5)** : (8) `Creating` est MODAL : seuls Échap (annule : le jeton passe dans `AppState.cancelled_drafts`) et Ctrl+c agissent ; les touches tapées pendant la création sont ignorées, jamais mises en file. La réponse tardive d'une création annulée est ignorée et son brouillon orphelin supprimé (`DeleteDraft`) ; une réponse de jeton jamais émis est ignorée sans rien supprimer. (9) Toute intention `Quit` (`panes::quit`, donc Ctrl+c comme `q`) avec un brouillon modifié ouvre la confirmation de fermeture au lieu de quitter ; « enregistrer » quitte à la confirmation du moteur, « abandonner » supprime le brouillon jamais enregistré puis quitte, « continuer » ou un enregistrement refusé annule la sortie. Sans modification, sortie directe inchangée. Limite (révisée à la revue de l'étape 2) : SIGTERM/SIGINT/SIGHUP (fermeture de la fenêtre du terminal) et la fermeture du clavier (`Wake::KeysClosed`) ne passent pas par la confirmation, mais avant de quitter la boucle émet l'`UpdateDraft` des champs modifiés du brouillon ouvert (`update::shutdown::shutdown_commands`) ; l'attente bornée des requêtes en vol (3 s, AG-38) le laisse aboutir. Ce chemin ne supprime jamais le brouillon. Reste possible : si un Ctrl+s est encore en vol, les deux enregistrements partent en parallèle et l'ordre d'arrivée au moteur n'est pas garanti. (10) Un nom d'affichage entre guillemets contenant `<` est relu (dernier `<` hors guillemets). (11) Reporté : collage par blocs (`Event::Paste` ignoré, Tab collé = champ suivant, insertion O(n) par caractère).
- **Raison** : solution la plus simple qui tient les invariants de l'étape 1 (réponses tardives ignorées, rien ne ferme une saisie ouverte, rien de brut vers le terminal).
- **Retour arrière** : n'envoyer aucun champ tant qu'une adresse est invalide (tout ou rien) dans `ComposeState::plan_field` ; garder tous les brouillons à la fermeture en retirant la commande de `close::close_now`.

## AG-43 — TUI : envoi, boîte d'envoi et file d'actions (étape 2, tâche 11)
- **Contexte** : envoyer est irréversible ; le plan cite le double envoi comme risque n° 5 (Ctrl+Entrée deux fois, envoi relancé). Le moteur dédoublonne `SendDraft` par clé d'idempotence (même clé → même action), met l'envoi en file avec un délai d'annulation de 10 s et ne renvoie jamais seul un envoi `uncertain` (invariant 26, `ResolveUncertainSend`). `SendDraft` répond `Action(id)` dès la mise en file, sans attendre le réseau.
- **Choix** : (1) **Clé d'envoi** : `ComposeState::send_key` est créée (`fresh_key("send")`, nonce de session) au premier départ de `SendDraft` du brouillon ouvert et réutilisée à chaque renvoi de ce brouillon, y compris après un échec ou une modification ; jamais de nouvelle clé pour le même `ComposeState`. (2) **Confirmation** : seul un geste délibéré ouvre la confirmation : **F5** (jamais du texte, montré dans le pied de page et l'aide de l'éditeur) ou un **Ctrl+Entrée réel**. Sans protocole clavier étendu, Ctrl+Entrée arrive comme Entrée ; le TUI pose donc le protocole kitty au seul niveau `DISAMBIGUATE_ESCAPE_CODES` quand `supports_keyboard_enhancement()` le permet (`app::keyboard_flags`, posé par `TerminalGuard::enter`, retiré par sa destruction — donc aussi sur sortie par signal — et par le crochet de panique, une seule fois). **Ctrl+j est un saut de ligne** (correction 1 : comme touche d'envoi, `Ctrl+j` puis « you » confirmait un message inachevé par le `y`). Le geste vérifie À/Cc/Cci (au moins une adresse valide, sinon champ signalé et message, rien d'envoyé) puis ouvre `Popup::ConfirmSend` ; Entrée/`y` confirme, Échap/`n` annule. La confirmation est un **résumé** (correction 1) : total des destinataires, une ligne par champ avec les adresses qui tiennent puis « (+N autres) », Cci en nombre seulement, objet toujours visible raccourci avec « … », ligne des touches toujours présente ; hauteur calculée d'après ce contenu (bornée par l'écran), tout via `display_safe`. (3) **Ordre** : modifications non enregistrées → `UpdateDraft` d'abord (phase `Saving`), `SendDraft` seulement à la confirmation du moteur ; échec de l'enregistrement → aucun envoi. (4) **En vol** (`Saving` ou `Sending`) : Ctrl+Entrée, frappe, Ctrl+s et Échap sont ignorés (« Envoi en cours ») ; le contenu ne peut donc pas changer entre la confirmation et la réponse. Succès : l'éditeur se ferme sans `DeleteDraft` (le brouillon appartient à l'envoi), « En file d'envoi » ; échec : texte intact, erreur affichée, même clé au renvoi. Réponse d'un autre brouillon, d'une autre clé ou hors envoi en vol : ignorée. (5) **Quitter** : pendant `Sending`, la sortie est immédiate — la requête est déjà partie, la boucle attend au plus 3 s les requêtes en vol (AG-38) et la mise en file est une écriture locale ; l'envoi est alors dans la file du moteur et sera rejoué avec sa clé au prochain lancement. Un second envoi avec une autre clé au prochain lancement est refusé par le moteur (brouillon `Scheduled`, `draft_not_editable`). Pendant `Saving` (rien n'est encore parti), quitter abandonne l'envoi et suit le chemin habituel du brouillon modifié (AG-42). (6) **Envoi incertain** : jamais de fenêtre automatique (une fenêtre surgissant sous une frappe pourrait être validée par erreur) ; l'événement `SendUncertain` ne fait qu'avertir dans la barre d'état ; la décision s'ouvre depuis la vue « file » (`u`/Entrée sur une fiche incertaine) et exige `r` (renvoyer) ou `n` (ne pas renvoyer) — Entrée ne décide rien, Échap remet à plus tard. (7) **Vue « file »** (`Q` depuis la liste et le lecteur, jamais pendant l'édition) : `ListOutbox` + `ListActions{Pending, InProgress, Failed, Uncertain}` (les `Send` de la file écartés, déjà dans la boîte d'envoi), fenêtrée ; `r` = `RetryAction` (échouées seulement, même action donc même clé), `x` = `CancelSend`/`CancelAction` (en attente seulement). Lectures étiquetées par compte et tour (`Tag::Outbox{account, round}`) : une réponse d'un autre compte, d'un tour périmé ou vue fermée est ignorée ; les événements d'action/envoi du compte relisent la vue, un seul tour de plus pendant une lecture. Le changement de compte sélectionné ferme la vue.
- **Revue de l'étape 2** : (8) un envoi demandé (F5) annule une fermeture ou une sortie demandée avant (`close_after_save`, `then_quit`) ; la fermeture n'a jamais lieu pendant `Saving`/`Sending`, et la confirmation d'envoi ne survit pas à son brouillon. ## AG-44 — TUI : vue « Brouillons » et reprise d'un brouillon enregistré (étape 2, tâche 11b)
- **Contexte** : la spec du TUI (§1, étape 2) liste les brouillons, mais `ListDrafts`/`GetDraft` n'étaient utilisées nulle part : un brouillon enregistré, ou repassé en `Editing` après `x` (annulation d'envoi) ou `n` (envoi incertain non renvoyé), ne pouvait plus être rouvert (limite notée en AG-43). Le moteur rend tout brouillon par `GetDraft`, quel que soit son état, mais refuse modification et suppression d'un brouillon planifié ou en cours d'envoi (`draft_not_editable`).
- **Choix** : (1) **Ouverture** : `B` depuis la liste, les résultats de recherche et le lecteur (jamais dans la barre latérale, l'éditeur, `Creating`, une fenêtre, la saisie de recherche ni la vue « file ») ouvre la vue `Brouillons` du compte sélectionné (`ListDrafts`, ordre du moteur : le plus récemment modifié d'abord). La vue est MODALE comme la file : seules `j`/`k`/↓/↑/`g`/`G`, Entrée, `D`, Échap et `q` y agissent ; aucune touche de courrier ne fuit vers l'arrière-plan. Lectures suivies par un jeton (`Tag::Drafts(u64)`, compteur jamais remis à zéro) : une réponse d'une vue fermée, d'un autre compte (le changement de compte ferme la vue et sa confirmation) ou d'une lecture périmée est ignorée ; les événements d'action/envoi du compte relisent la vue (un seul tour de plus pendant une lecture), la liste affichée reste en place jusqu'à la réponse. (2) **Sélection ancrée sur le `DraftId`** : un brouillon disparu d'une relecture n'est remplacé par aucun autre ; Entrée et `D` répondent alors « Ce brouillon n'existe plus ». (3) **Réouverture** : Entrée sur un brouillon en édition envoie `GetDraft` (`Tag::DraftLoaded(u64)`) ; un seul à la fois, la réponse n'est prise que pour la vue ouverte et un éditeur fermé. L'éditeur est construit par `ComposeState::from_saved_draft` : champs À/Cc/Cci/Objet/Corps du brouillon relu, référence = contenu chargé (`has_unsaved()` faux), `saved_once = true`, `send_key = None`, compte du brouillon (ligne « De : »). La vue se ferme à l'ouverture de l'éditeur (Échap de l'éditeur revient à la liste ; `B` rouvre la vue). (4) **États non modifiables** : un brouillon planifié ou en cours d'envoi est montré avec son état (« planifié », « en cours d'envoi ») ; Entrée répond par un message clair (annuler l'envoi depuis la file `Q`) sans requête et la vue reste ouverte ; même chose si la relecture révèle que l'état a changé entre-temps. (5) **Suppression en deux temps** : `D` ouvre `Popup::ConfirmDeleteDraft { draft, subject }` sur le brouillon sélectionné (identifiant pris au premier `D`) ; seul un second `D` sans Ctrl ni Alt envoie `DeleteDraft` ; TOUTE autre touche (Échap, Entrée, `y`, `d`, Ctrl+D, Alt+D…) annule sans rien détruire, et la touche n'est pas appliquée. La liste ne change qu'à la réponse du moteur : succès annoncé (« Brouillon « X » supprimé ») et vue relue ; refus (brouillon planifié : `draft_not_editable`) affiché tel quel, liste inchangée. La suppression n'est pas refusée localement : le moteur reste seul juge. (6) **Abandon d'un brouillon rouvert** : `close_now` ne supprime jamais un brouillon `saved_once` ; « abandonner » (`D` puis `D` dans la fermeture, y compris depuis Ctrl+c) n'abandonne donc que les modifications non enregistrées, le brouillon du moteur garde sa dernière version enregistrée ; la seconde fenêtre le dit (« La version enregistrée est gardée »). Fermer sans modification ne produit aucune commande. (7) Les messages « Envoi abandonné : le brouillon revient en édition » et « Envoi « X » annulé… » ajoutent « (rouvrez-le avec B) ». (8) Tout texte du courrier ou du moteur (objet, destinataires, erreurs) passe par `display_safe` ; seules les lignes visibles sont construites (5 000 brouillons testés).
- **Raison** : solution la plus simple qui reprend le schéma déjà revu de la vue « file » (jetons, ancrage, modale) et les gestes délibérés de l'étape 2 ; aucun chemin ne détruit un brouillon enregistré sans `D` `D` explicite.
- **Retour arrière** : retirer `B` de `input::list::MESSAGE_KEYS` (la vue devient inaccessible) ; garder la vue ouverte sous l'éditeur en ne la fermant plus dans `update::drafts::reopen::open_in_editor` (et la relire à la fermeture de l'éditeur).

## AG-45 — Interface Flutter : pont FFI (flutter_rust_bridge) vers le moteur, lecture seule
- **Contexte** : l'utilisateur impose une façade FFI (`flutter_rust_bridge`) entre l'app Flutter (`app/`) et le moteur, au lieu du CLI `--json`. Deux règles du projet s'y opposent : `unsafe_code = "forbid"` (règle 6) et les normes de codage (fonctions ≤ 30 lignes, pas de commentaire en corps), alors que le code généré par FRB contient du `unsafe`, des `unwrap` et des fonctions longues.
- **Choix** : (1) le pont est un crate **hors du workspace du moteur** (`bridge/`, son propre `[workspace]`, dépend seulement de `mira-assembly` : frontière A4 respectée) ; le moteur, son `ci.sh` et ses garde-fous ne changent pas et `unsafe` reste interdit dans `engine/`. (2) Le code écrit à la main dans `bridge/src` (hors `frb_generated.rs`) suit les normes (`tools/check-norms` vert) ; seul `frb_generated.rs` est exempté (`#[allow(clippy::unwrap_used…)]` sur le module). (3) L'API FFI est volontairement mince et stable : `open_engine(profile)`, `execute(request_json)`, `watch_events(after, sink)`, `close_engine()`, `contract_version()`. Tout passe par des chaînes JSON de l'enveloppe versionnée `{contract_version, ok, data | error}` (celle du CLI, invariant 33) : le contrat `Request`/`Response` de `mira-core` reste la seule source de vérité, sans miroir `#[frb(mirror)]` de ~200 types ; Dart décode ce dont l'écran a besoin (`app/lib/engine/mappers.dart`). (4) Version du codegen épinglée à 2.11.1 (installé hors du dépôt : `cargo install flutter_rust_bridge_codegen --version 2.11.1 --locked --root <dossier>`, le `flutter_rust_bridge_codegen` du système est un 1.80.1 de rustdesk, incompatible) ; génération : `cd app && RUSTC_BOOTSTRAP=1 flutter_rust_bridge_codegen generate` (`cargo expand` doit tourner sur la chaîne 1.99 : `bridge/rust-toolchain.toml`). (5) Pas de cargokit/`rust_builder` : la bibliothèque est compilée à la main (`cd bridge && cargo build --release`) et trouvée par `MIRA_BRIDGE_LIB`, `../bridge/target/{release,debug}/libmira_bridge.so` ou le chargeur système. Linux seulement pour l'instant.
- **Données** : au démarrage `main.dart` ouvre le profil `default` (trousseau et dossier de données du système, `MIRA_HOME` pour un profil de test), lit comptes → boîtes → première page (200) de chaque boîte de rôle inbox/sent/drafts/trash/junk/archive, regroupe par fil (`thread`) et par dossier en « conversations » (`MailStore.source`, `EngineMailSource`). Le corps (texte ou HTML déjà assaini par `get_safe_html`) et les pièces jointes sont lus **à l'ouverture** d'une conversation (`hydrate`) ; un corps absent hors ligne déclenche `fetch_message_body` (commande réseau explicite, geste de l'utilisateur). Les événements `sync_finished`, `new_message_received`, `message_updated`, `message_deleted`, `mailbox_counters_updated`, `body_available` relisent la boîte du compte. Sans compte, un compte vide « Aucun compte » et un toast. Si le moteur ne s'ouvre pas (bibliothèque absente, profil verrouillé par le TUI), l'app retombe sur les données de démonstration et l'écrit sur stderr ; `MIRA_DEMO=1` les force.
- **Limites assumées (étape suivante)** : tout ce qui écrit reste local à l'écran et n'atteint pas le moteur (archiver, corbeille, étoile, lu/non lu, libellés, report) ; **l'envoi est refusé** avec un message d'erreur plutôt que simulé (`MailStore.send`), les réponses automatiques et mails entrants fictifs sont désactivés avec un moteur réel ; l'ajout de compte de l'interface reste fictif ; une seule page de 200 messages par boîte (pas de défilement paginé) ; le profil est verrouillé : TUI et Flutter ne tournent pas en même temps.
- **Raison** : seule façon d'obtenir une façade FFI sans toucher aux garde-fous du moteur ni dupliquer son contrat ; JSON = réversible et testable des deux côtés (test Rust de bout en bout contre le faux serveur IMAP, test Dart avec faux client + test Dart par FFI réel).
- **Retour arrière** : supprimer `bridge/` et `app/lib/src/rust`, `app/lib/engine/rust_engine_client.dart` ; passer `source: null` dans `main.dart` (données de démonstration) ou écrire un `EngineClient` qui appelle `mira --json`.

## AG-46 — Interface Flutter : rendu du HTML des messages, images incorporées et contenu distant
- **Contexte** : `parseHtml` (mini-parseur d'origine, `p/strong/em/br/a/blockquote`) ignorait tableaux, images, titres, listes : les vrais courriels s'affichaient en texte aplati, sans image.
- **Choix** : (1) le HTML **déjà assaini par le moteur** (`get_safe_html`, ammonia : script, gestionnaires et ressources distantes retirés) est rendu par `flutter_widget_from_html_core` (+ `html`, dépendances pub.dev ajoutées au même titre que les crates ; contenu de paquet = code, pas instruction). `Msg.html` porte ce HTML ; `Msg.body` (blocs) reste le texte brut du moteur, utilisé pour les réponses, citations, extraits et recherche. (2) **Images** : `data:image/*` décodées sur place ; `cid:` résolues en enregistrant la pièce jointe incorporée (`save_attachment` vers un dossier temporaire, lecture puis suppression ; ≤ 20 images, ≤ 5 Mo chacune) et masquées de la liste des pièces jointes ; **images distantes jamais chargées d'office** : le moteur les retire et les signale (`blocked_resources`), un bandeau propose « Afficher » (`allow_remote_content` sur le message) ou « Toujours pour cet expéditeur » (`scope: sender`), puis le HTML est relu. (3) **Couleurs** : un HTML qui impose ses couleurs (`color`, `bgcolor`, `background`) est posé sur une carte blanche (texte `#1a1a1a`) pour rester lisible en thème sombre ; sinon il suit la palette de l'app. (4) **Liens** : seuls `http`, `https` et `mailto` s'ouvrent (`xdg-open`, Linux) ; `javascript:`, `file:` etc. sont refusés.
- **Limites** : pas de lien `mailto:` vers le composeur (ouvre le client système), pas de mode sombre automatique des courriels clairs, images distantes non mises en cache, SVG non rendus, largeur fixe des tableaux larges non réduite.
- **Retour arrière** : ne plus renseigner `Msg.html` dans `EngineMailSource._loadSafeHtml` (retour à l'affichage par blocs).

## AG-47 — Interface Flutter : HTML d'origine sans assainissement (demande explicite de l'utilisateur)
- **Contexte** : l'assainissement du moteur (ammonia) retire `<style>` et les attributs `style`/`class` : les courriels perdaient mise en page et couleurs (capture de l'utilisateur, AG-46). L'utilisateur demande l'HTML « tel quel, avec sa structure et ses couleurs ». Le contrat du moteur n'expose que `get_safe_html` (assaini) et `get_raw_source`.
- **Choix** : (1) **le moteur et son contrat ne changent pas** : le pont (`bridge/src/original_html.rs`, fonction FFI `get_original_html`) lit `get_raw_source` (source locale), l'analyse avec `mail-parser` (mêmes parties `html_body` que le moteur) et rend l'HTML brut ; texte seul → `null`. (2) Côté Dart, les règles des `<style>` sont reportées dans les `style` en ligne (`css_inliner.dart`, csslib + html ; `@media`, pseudo-classes et sélecteurs non gérés ignorés) car `flutter_widget_from_html_core` ignore `<style>` ; le HTML est ensuite rendu avec ses couleurs sur carte blanche (AG-46). (3) **Ce qui reste protégé malgré l'absence d'assainissement** : le moteur d'affichage n'exécute aucun script ni gestionnaire d'événement ; les images distantes ne sont chargées que si `get_safe_html` n'en signale plus de bloquées (consentement `allow_remote_content` par message ou expéditeur, bandeau inchangé) ; les liens ne s'ouvrent que pour `http`, `https`, `mailto`. `get_safe_html` ne sert plus qu'à connaître le consentement et à servir de repli si la source brute manque.
- **Risque assumé** : un HTML non assaini est un contenu hostile traité par l'analyseur HTML/CSS du client (pas de script, mais bogues d'analyse ou grosses pages possibles) ; la page n'est pas bornée en taille.
- **Retour arrière** : dans `EngineMailSource._loadSafeHtml`, utiliser `safe['html']` au lieu de `originalHtml` (retour à AG-46).

## AG-48 — Interface Flutter : politique des images distantes (Paramètres › Messagerie)
- **Contexte** : le consentement du moteur (`allow_remote_content`) ne connaît que « ce message » et « cet expéditeur » ; l'utilisateur veut décider une fois pour toutes, avec des règles par adresse ou domaine.
- **Choix** : (1) réglage général `Demander` (défaut) / `Toujours afficher` / `Ne jamais afficher`, plus une liste de règles `adresse ou domaine → toujours | jamais`. Décision (`ImagePolicy.decide`, `app/lib/state/image_policy.dart`) : adresse exacte, puis domaine **le plus précis** (un domaine couvre ses sous-domaines, pas `notexemple.com`), puis réglage général. (2) Stockée dans les préférences de l'app (`imgPolicy`, JSON), pas dans le moteur : le moteur n'a pas de notion de domaine et l'HTML d'origine est rendu côté client (AG-47). (3) Effet : `toujours` charge les images distantes même si le moteur les signale bloquées ; `jamais` ne charge rien, même si le moteur a un consentement, et masque le bandeau ; `demander` garde le bandeau (« Afficher » = consentement moteur du message). « Toujours pour cet expéditeur » ajoute aussi une règle visible et supprimable dans les paramètres. (4) Saisie validée (`nom@domaine.tld` ou `domaine.tld`), normalisée en minuscules ; données enregistrées illisibles → « demander ».
- **Limite** : la politique vaut pour l'app Flutter, pas pour le TUI ni le CLI (qui utilisent le consentement du moteur).
- **Retour arrière** : retirer `ImageRulesSection` de l'onglet Messagerie et lire `msg.blocked.isEmpty` seul dans `MailHtml`.

## AG-49 — Lenteur et mémoire de l'app Flutter : rejeu du journal, rafales d'événements, HTML reconstruit
- **Contexte** : l'app devenait lente et gourmande en mémoire. Causes trouvées : (1) `watch_events(after: null)` s'abonnait « depuis le début » (le moteur rejoue tout le journal depuis la base) et chaque événement `sync_finished`/`body_available`/… déclenchait une relecture complète de la boîte ; (2) aucune coalescence : une synchro émet des milliers d'événements ; (3) toute relecture remplaçait la liste et redessinait tout, même sans changement ; (4) `HtmlWidget` réanalysait le HTML à chaque notification du store.
- **Choix** : (1) le pont, sans numéro de départ, ne livre que les événements **futurs** (`latest_seq` parcourt le journal par pages de 500, comme le TUI, AG-41) ; (2) l'app ne réagit plus qu'à `sync_finished`, `new_message_received`, `message_updated`, `message_deleted` (plus `body_available` ni `mailbox_counters_updated`), regroupés par compte avec 800 ms de calme ; (3) une seule relecture par compte à la fois (une demande en plus pendant la lecture = une relecture après) et **aucun redessin si l'empreinte de la liste n'a pas changé** ; (4) `MailHtml` ne reconstruit l'arbre HTML que si le HTML, le thème ou la décision d'images change ; (5) `dispose` n'attend plus l'annulation du flux FFI (elle ne se termine qu'à la fermeture du moteur).
- **À savoir** : `flutter run` en debug avec `--track-widget-creation` et `--start-paused` est nettement plus lent qu'en `--profile`/`--release` ; juger la fluidité hors debug.
- **Retour arrière** : `watch_events` avec `after: Some(0)` rejoue tout ; remettre `debounce: Duration.zero`.

## AG-50 — Interface Flutter : transition au chargement d'un message
- **Contexte** : passer d'un message à l'autre affichait l'aperçu, puis (≈ 50 ms plus tard) remplaçait brusquement le corps par le HTML, dont l'analyse et la mise en page bloquaient le fil d'interface.
- **Choix** : (1) pendant la lecture du corps (`Msg.loaded` faux), un **squelette** pulsant remplace l'aperçu ; fondu de 160 ms vers le texte ou le HTML (`_BodySwitch`). (2) `HtmlWidget` en `buildAsync: true` : l'analyse du HTML se fait dans un isolat ; le squelette reste visible puis le HTML apparaît en fondu et la hauteur s'anime (`AnimatedSize`, 180 ms). (3) **Préchargement** des deux conversations voisines à l'ouverture d'un message (`_prefetchAround`) : `j`/`k` n'attendent plus le moteur.
- **Limite** : la mise en page du HTML reste sur le fil d'interface (seule l'analyse est déportée) ; une très grosse newsletter peut encore saccader brièvement.
- **Retour arrière** : `buildAsync: false` dans `MailHtml`, retirer `_BodySwitch` et `_prefetchAround`.
- **Correctif (AG-50)** : la carte blanche des courriels colorés était **hors** du fondu et apparaissait d'un coup sur le thème sombre (éblouissement). Elle est maintenant à l'intérieur : opacité 0 → 1 en 320 ms (`easeInOut`), hauteur animée sur 260 ms ; test dédié (`html_body_test.dart`).
- **Délai d'affichage (AG-50, suite)** : 1 à 2 s avant le corps. Causes côté app : étapes en série (corps → HTML assaini → HTML d'origine → pièces jointes → images incorporées, interrogées toutes les 100 ms), `inlineStyles` sur le fil d'interface, isolat lancé pour tout HTML. Changements : HTML assaini et d'origine lus **en parallèle**, `inlineStyles` dans un isolat (`compute`), messages d'une conversation chargés en parallèle, le corps s'affiche **dès qu'il est prêt** (`onProgress`) et pièces jointes/images incorporées arrivent ensuite (sondage 20 ms, en parallèle), analyse HTML en isolat seulement au-delà de 30 000 caractères, **préchargement** des 8 premières conversations au démarrage et des voisins à l'ouverture. Reste hors de portée de l'app : un corps non encore téléchargé exige un aller-retour IMAP (`fetch_message_body`). `MIRA_TRACE=1` affiche la durée par message (`corps`, `pièces jointes`) pour savoir où part le temps.

## AG-51 — Fluidité du lecteur : mesures, pile de conversations hors écran
- **Mesures** (banc d'essai sur une newsletter synthétique de 60 blocs ≈ 26 ko, tableaux imbriqués) : construction + mise en page de `HtmlWidget` ≈ **1,1 à 1,6 s en debug (JIT)** contre ≈ **170 ms en `--profile` (AOT)** ; 200 blocs (88 ko) : ≈ 2,5 s contre ≈ 670 ms (rastérisation logicielle sous Xvfb comprise). Les images et les attributs `style` représentent l'essentiel du coût ; le moteur Rust (lecture, HTML d'origine) et `inlineStyles` restent à quelques dizaines de ms. Le **mode debug** (`flutter run`, JIT, assertions, `--track-widget-creation`) multiplie donc le temps par 5 à 10 : la fluidité se juge en `--profile`/`--release`.
- **Choix** : (1) les 5 dernières conversations affichées restent **montées hors écran** (`Offstage` + `TickerMode`, `_Deck`) avec leur position de défilement ; y revenir ne reconstruit rien ; (2) les **voisins** (suivant puis précédent) sont montés hors écran après 450 ms de calme, un par un, une fois la conversation courante chargée : `j`/`k` affichent une page déjà mise en page, avec un fondu de 150 ms ; (3) le lecteur n'est plus recréé à chaque message (clé fixe) : seule la barre d'actions suit la conversation courante.
- **Coût** : mémoire (jusqu'à 5 arbres HTML) et un à-coup au moment du montage hors écran (≈ 0,2 à 0,7 s en profile pour une grosse newsletter, au calme) ; plafond `_deckSize`.
- **Non fait / limites** : la mise en page du HTML reste sur le fil d'interface (pas de rendu partiel d'une page unique) ; une conversation jamais vue ni préchargée paie encore le plein coût à sa première ouverture.
- **Retour arrière** : `ValueKey(m.id)` dans `shell.dart` et `_deckSize = 1`.

## AG-52 — Interface Flutter : panneau d'ajout de compte et Makefile
- **Contexte** : l'ajout de compte de l'interface était fictif (nom + adresse). Le moteur expose le catalogue des providers, la préparation d'une adresse, le test de connexion, l'ajout, et le flux OAuth (`start_oauth` → navigateur → `complete_oauth` → `add_account` avec `oauth_flow`).
- **Choix** : (1) vrai **panneau** (`PaneView.addAccount`, ouvert par le menu des comptes et par Paramètres › Compte) : boutons des fournisseurs lus dans `list_providers` (dont « Autre (IMAP / SMTP) », le fournisseur sans domaine), identité, méthodes d'authentification proposées par le fournisseur (OAuth, mot de passe d'application, mot de passe), formulaire **détaillé** IMAP/SMTP (hôte, port, TLS / STARTTLS / aucun) seulement pour « Autre » — comme le contrat (`servers` n'est saisi que pour le repli) ; les serveurs sont préremplis par `prepare_account` dès qu'une adresse valide est saisie (détection automatique du fournisseur si aucun n'est choisi). (2) « Tester la connexion » (`test_connection`, rien n'est enregistré) et « Ajouter le compte » (`add_account`, secret envoyé une fois puis champ vidé, jamais affiché ni journalisé ; clé d'idempotence stable pour les mêmes valeurs saisies, donc un renvoi ne crée pas de doublon). (3) OAuth : la page d'autorisation s'ouvre dans le navigateur (`xdg-open`, http/https seulement ; sinon l'adresse s'affiche), bouton « Annuler » (`cancel_oauth`), annulation aussi à la fermeture du panneau ; si le moteur n'a pas d'identifiants OAuth configurés l'erreur du moteur s'affiche et l'on bascule sur le mot de passe d'application. (4) Après l'ajout : `start_sync` du compte, liste relue, bascule sur le nouveau compte. Erreurs du moteur affichées telles quelles (sans secret). (5) **Makefile** à la racine : `make run` (pont + dépendances + `flutter run`, `MODE=profile` par défaut), `demo`, `tui`, `cli`, `build`, `codegen`, `check-all`, `test-all`, `lint`, `norms`, `setup`, `clean*` ; `make help` les liste. Il a servi tout de suite : `make norms` a révélé que `runtime.rs` dépassait 6 fonctions, le flux d'événements est passé dans `events_feed.rs`.
- **Limites** : pas de saisie d'un nom d'utilisateur distinct de l'adresse (le contrat n'en a pas) ; pas de modification ni de suppression de compte dans le panneau ; l'OAuth dépend de la configuration du moteur (identifiants client), non testée contre un vrai fournisseur.
- **Retour arrière** : `openAddAccount` → `showAddAccountDialog` dans le menu des comptes (fenêtre fictive).

## AG-53 — Synchronisation : actualisation manuelle, retour de focus, fréquence de relevé
- **Contexte** : la Réception est poussée par IDLE (≈ 1–2 s) mais le reste n'est relevé qu'au délai du fournisseur (Gmail/Outlook 120 s, Yahoo et « Autre » 300 s), et l'app n'avait aucun moyen de forcer une synchro.
- **Choix** : (1) regroupement des événements ramené de 800 à **150 ms** ; (2) **Actualiser** : bouton dans l'en-tête de la liste, `F5` ou `Ctrl+R` → `start_sync` de tous les comptes + relecture immédiate de la boîte active ; (3) **retour de focus** de la fenêtre → même actualisation, silencieuse, au plus toutes les 30 s ; (4) réglage **Fréquence de relevé** (Paramètres › Messagerie : Auto, 30 s, 1, 2, 5 min) transmis au moteur à l'ouverture (`open_engine(profile, poll_secs)` → `SupervisorConfig.poll_interval`), **borné de 30 s à 1 h** par le pont (`polling.rs`), appliqué au prochain lancement ; « Auto » garde le délai du fournisseur.
- **Risque assumé** : descendre sous le délai du fournisseur peut faire limiter ou bloquer le compte (Gmail surtout) ; le plancher de 30 s et la mention dans les réglages en sont la seule protection.
- **Reste hors portée** : IDLE sur d'autres dossiers que la Réception (une connexion par dossier, plafond 3 à 5), push natif des fournisseurs (serveur intermédiaire).
- **Retour arrière** : `poll_secs = None` (Auto) ; retirer le bouton et `refreshNow`.

## AG-54 — Paramètres › Comptes : gestion des comptes et des identités
- **Contexte** : l'onglet « Compte » n'affichait que le nom et un bouton de démonstration. Le contrat expose `update_account`, `pause/resume/delete_account`, `reauthenticate`/`store_app_password`, et les opérations d'identités (`list`, `add`, `update`, `set_default`).
- **Choix** : (1) l'onglet devient **Comptes** (moteur réel) : un bloc dépliable par compte avec son **état** (connecté, hors ligne, reconnexion nécessaire, en pause, erreur) et le nombre d'**actions en attente** (`get_status`). (2) Dans le bloc : nom affiché (`update_account`), **fenêtre de synchronisation** 30/90/180/365 jours, **Synchroniser maintenant**, **Pause / Reprendre**, **serveurs IMAP/SMTP** modifiables (pour les comptes qui en ont ; le moteur vérifie la connexion avant d'accepter), **reconnexion** (OAuth : flux navigateur ; mot de passe : `store_app_password`, champ vidé après envoi), **identités** (modifier nom et signature, définir par défaut, ajouter alias / autre nom), **suppression** en deux temps (avertit des actions en attente ; le moteur efface messages locaux, brouillons, secrets et file ; le courrier reste sur le serveur). (3) `MailStore.accountsChanged` relit les comptes, retire les boîtes supprimées, bascule sur un autre compte si l'actif disparaît, **sans quitter les réglages**.
- **Limites** : le contrat n'offre ni suppression ni changement d'adresse d'une identité (elles restent) ; les identités ne sont pas encore proposées comme expéditeur dans le composeur ; l'adresse et le fournisseur d'un compte ne sont pas modifiables (supprimer puis ajouter) ; le choix des boîtes synchronisées n'est pas exposé.
- **Retour arrière** : remettre l'ancienne branche `_ =>` de l'onglet dans `settings_panel.dart`.

## AG-55 — Identités : composeur, adresses détectées, ce que le courrier ne dit pas
- **Contexte** : l'utilisateur attendait que les identités viennent avec le compte (ex. alias `iam@…` d'un compte Gmail, déclaré dans « Envoyer des e-mails en tant que »). **Ce n'est pas lisible par IMAP/SMTP** : la liste des alias est un réglage du fournisseur (API Gmail `sendAs`, pas le protocole) ; le moteur ne connaît que les identités qu'on lui enregistre (une par compte à l'ajout, puis les ajouts manuels).
- **Choix** : (1) **composeur** : le sélecteur « De » propose les identités de tous les comptes (compte actif d'abord, défaut en tête), plus les comptes sans identité ; un nouveau message part de l'identité **par défaut** du compte actif ; une **réponse** part de l'identité à laquelle le message a été adressé (À/Cc), sinon du défaut du compte ; la **signature** est celle de l'identité (sinon la signature générale). Les adresses d'identités comptent comme « miennes » (pas de réponse à soi-même, pas de copie à soi). (2) **Adresses détectées** : dans Paramètres › Comptes, MIRA propose en un clic les adresses vues dans les messages déjà synchronisés — expéditeur de messages envoyés, destinataire unique de messages reçus (`alias_hints.dart`) — qui ne sont pas déjà des identités ; limite : 200 derniers messages par boîte. (3) Les identités sont relues après chaque modification (`identitiesChanged`).
- **À savoir (à dire à l'utilisateur)** : un alias doit être **déclaré chez le fournisseur** pour que le serveur accepte d'envoyer sous cette adresse (Gmail réécrit sinon l'expéditeur) ; et **l'envoi réel n'est pas encore branché sur le moteur** (l'app le refuse, AG-45) : choisir une identité n'a donc pas encore d'effet sur un courrier envoyé.
- **Option non faite** : importer les alias Gmail par l'API Gmail (portée `gmail.settings.basic`, hors IMAP) — demande un client OAuth Google et un appel HTTP du moteur.
- **Retour arrière** : `senderChoices` → comptes seuls ; retirer `_hints` de `identities_box.dart`.

## AG-56 — Assainissement HTML borné en taille et en profondeur (corrige AG-34)
- **Contexte** : `sanitize_html` était quadratique en profondeur d'imbrication (10 000 `<div>` : 5 s ; 100 000 : plus de 10 min). Un message piégé gelait l'affichage.
- **Choix** : `html/limits.rs` mesure l'entrée **avant** `ammonia`. Au-delà de 2 Mio ou de 512 balises ouvertes en même temps, le message est rendu en texte tronqué et échappé dans un `<pre>`, sans balise active ni ressource distante. En deçà, le chemin d'origine est inchangé. La profondeur est estimée sans analyseur HTML (balises vides exclues, une fermeture décrémente).
- **Limites** : un vrai message avec plus de 512 balises non fermées (`<p>`, `<li>`) serait affiché en texte brut ; la mise en forme est alors perdue, jamais la sécurité.
- **Retour arrière** : retirer le garde `is_within_limits` de `sanitize_html`.

## AG-57 — Lectures explicites : jeton OAuth rafraîchi par `ImapAccess` (corrige la limite d'AG-22/AG-27)
- **Contexte** : la synchro et le rejeu rafraîchissaient déjà le jeton d'accès, mais `ImapAccess` (corps, pièces jointes, recherche serveur) utilisait le jeton rangé tel quel : une fois expiré, ces commandes échouaient en `authentication.token_expired` jusqu'à la prochaine synchro.
- **Choix** : `ImapAccess` détient la configuration du moteur et la base, et se connecte comme le rejeu : `renew_access_token` si le jeton est expiré, puis, sur un refus d'authentification, un rafraîchissement forcé et une seule nouvelle tentative. Sans effet pour les comptes à mot de passe.
- **Limites** : le fournisseur d'identifiants reste dupliqué entre le rejeu (`ProductionCredentials`), la synchro (`ProfileCredentials`) et `ImapAccess` ; les unifier (AG-27) reste à faire.
- **Retour arrière** : restaurer l'ancienne `ImapAccess::connect` (lecture directe du coffre).

## AG-58 — Noms de boîtes en UTF-7 modifié et recherche `CHARSET UTF-8`
- **Contexte** : le client IMAP envoyait et lisait les noms de boîtes tels quels. Un serveur annonce « Éléments envoyés » en UTF-7 (`&AMk-l&AOk-ments envoy&AOk-s`) : le nom restait illisible, et le `SELECT` d'une boîte accentuée envoyait de l'UTF-8 brut entre guillemets (interdit par la RFC 3501). La recherche serveur d'un texte accentué envoyait aussi de l'UTF-8 entre guillemets.
- **Choix** : (1) `imap/protocol/mailbox_name.rs` encode et décode l'UTF-7 modifié (`&` doublé, blocs UTF-16 big-endian en base64 avec `,`). Le moteur ne manipule que du texte lisible : `parse_list` décode, `quote_mailbox` encode pour SELECT, APPEND, CREATE, RENAME, DELETE, COPY et MOVE. Un nom mal formé venant du serveur est gardé tel quel. Les caractères de contrôle restent refusés avant l'encodage. (2) Une requête `search_text` non ASCII part en `UID SEARCH CHARSET UTF-8 TEXT {n}` avec la requête en littéral ; une requête ASCII reste entre guillemets. (3) Le faux serveur IMAP refuse désormais tout octet non ASCII dans une chaîne entre guillemets, comme un vrai serveur ; il garde les noms de boîtes en UTF-7, tels que sur le fil.
- **Limites** : les libellés `X-GM-LABELS` (envoi) ne sont pas encodés en UTF-7, faute de vérification du comportement de Gmail ; `UTF8=ACCEPT` (RFC 6855) n'est pas négocié ; `SEARCH CHARSET UTF-8` suppose que le serveur l'accepte (RFC 3501 impose UTF-8 aux serveurs, non vérifié contre les vrais fournisseurs).
- **Retour arrière** : retirer `quote_mailbox` des opérations (retour à `quote`), le décodage dans `parse_list` et la branche non ASCII de `search_text`.

## AG-59 — Abandon du miroir : les traces sont effacées (corrige l'écart relevé après AG-33)
- **Contexte** : `maintenance::discard_mirror_and_cache` supprimait les lignes du miroir sans fusionner l'index FTS5 ni tronquer le journal WAL : des fragments de sujets et d'adresses restaient dans les fichiers de la base. La suppression d'un compte (`erase_account`) les effaçait déjà.
- **Choix** : l'opération appelle `Database::discard_mirror_of`, qui jette le miroir puis exécute `erase_traces`. Test de non-régression sur les fichiers (`maintenance_discard_traces.rs`) : le mot du compte jeté disparaît, celui de l'autre compte reste.
- **Limites** : aucune requête de la façade ni du pont n'appelle encore cette opération (D-18 « jeter le miroir ») : la correction ne protège que quand une interface l'expose. Pas de `VACUUM` ; les bases déjà écrites ne sont pas purgées rétroactivement (AG-33).
- **Retour arrière** : remettre `database.write(|tx| tx.discard_account_mirror(account))`.

## AG-60 — Audit : une erreur TLS pendant un envoi ne peut ni envoyer ni doubler un message
- **Contexte** : AG-30 laissait « à auditer » le classement d'une erreur `Tls` en cours d'envoi comme passagère (`classify` → `Transient`).
- **Constat** : dans le client SMTP, la catégorie `Tls` ne sort que de la négociation (`TlsParameters`, poignée de main, STARTTLS absent ou non chiffré), toujours avant la commande DATA. Une panne TLS survenue plus tard est une erreur d'entrée-sortie, classée `network.connection_lost` (issue incertaine, `settle_interrupted_send`). `send_outcome_is_unknown` ne compte donc pas `Tls`, à raison. Test de bout en bout ajouté (`send_tls_failure.rs`) : STARTTLS exigé et absent → `tls.handshake`, rien reçu par le serveur, 0 incertain, action en attente avec le code `tls.handshake`.
- **Aucun défaut de sécurité d'envoi.** Reste une limite d'expérience : un échec TLS permanent (certificat invalide, serveur sans STARTTLS) est rejoué avec un délai croissant et le compte passe « hors ligne », sans demander de décision à l'utilisateur. L'événement `CertificateNeedsApproval` n'est jamais émis (référence §14, « certificat à valider »). À traiter avec la fonctionnalité d'approbation de certificat, pas ici.
- **Retour arrière** : aucun changement de code ; supprimer le test.

## AG-61 — Désarchivage fait ailleurs : fusion de fin de passe (corrige la limite d'AG-28)
- **Contexte** : la réception est synchronisée avant les autres boîtes (D-20). Un message remis dans la réception depuis un autre appareil y arrive avec un nouvel UID alors que sa copie « Archive » est encore vivante dans le miroir : le recoupement refuse un jumeau vivant, le message est donc recréé, puis l'ancien devient orphelin et est supprimé. L'identifiant interne changeait (`id-000005` → `id-000009`), avec tout ce qui s'y rattache (données locales, corps déjà téléchargé).
- **Choix** : `SyncSession` garde les messages créés pendant la passe (`created_in_pass`, vidé à chaque `begin_pass`). Avant le ménage des orphelins d'une passe complète, `sync/download/twins.rs` apparie chaque orphelin à **un seul** message créé pendant la passe de même empreinte (Message-ID, date, taille), reporte les drapeaux du serveur sur l'orphelin, rattache au message conservé les apparitions et correspondances serveur du jumeau (`Tx::merge_twin_into`), puis supprime le jumeau. Plusieurs jumeaux possibles = ambigu, rien n'est fusionné. Une vraie copie dans deux boîtes (sans orphelin) n'est jamais touchée.
- **Limites** : le jumeau a déjà été annoncé (`NewMessageReceived`) avant la fusion ; il est ensuite retiré par `MessageDeleted` puis le message conservé par `MessageUpdated` : une notification « nouveau message » peut donc apparaître à tort pour un désarchivage. Des annonces différées en fin de passe l'éviteraient (non fait). Les passes interrompues ou avec une boîte ignorée ne fusionnent pas (les orphelins restent jusqu'à une passe complète).
- **Retour arrière** : retirer l'appel `merge_moved_twins` de `sync/download/account.rs`.

## AG-62 — Test de connexion : le SMTP est vérifié avec l'IMAP (corrige la limite d'AG-14)
- **Contexte** : à l'ajout d'un compte, seul l'IMAP était testé. Un serveur SMTP faux, injoignable ou refusant le mot de passe n'apparaissait qu'au premier envoi, donc tard et loin de la saisie.
- **Choix** : `smtp::check_smtp_login` se connecte, négocie le chiffrement et s'authentifie (`test_connection` de `lettre`), sans envoyer de message ; le clair hors boucle locale reste refusé (AG-03). `accounts::check_mail_login` vérifie l'IMAP (dans le budget de connexions du compte) puis le SMTP avec le même utilisateur et le même secret (XOAUTH2 pour OAuth2). Il remplace `check_imap_login` dans `TestConnection`, `AddAccount` et `UpdateAccount` (changement de serveurs). Un SMTP injoignable donne `network.unreachable` (réessayable), un refus `authentication.*`, et l'ajout n'enregistre rien.
- **Limites** : un compte ne peut plus être ajouté tant que son SMTP ne répond pas, même pour ne faire que lire (réseau qui bloque les ports d'envoi). Retour arrière simple si ce choix déplaît (ci-dessous). Un jeton OAuth2 obtenu sans la portée d'envoi du provider échouera ici plutôt qu'à l'envoi (cas voulu).
- **Tests** : `smtp_check_login.rs`, `api_accounts_smtp_check.rs`. La fixture de la façade démarre désormais un faux SMTP (identifiants partagés avec l'IMAP) ; `local_servers(imap, smtp)` prend les deux ports.
- **Retour arrière** : remettre `check_imap_login` dans les trois handlers.

## AG-63 — Retrait du CLI (`mira-cli`) et du TUI (`mira-tui`)
- **Contexte** : l'application Flutter, par le pont FFI, est le seul client utilisé ; le CLI et le TUI n'étaient plus développés et leurs tests de bout en bout pesaient lourd en mémoire et en temps de compilation pour la CI.
- **Choix** : décision de l'utilisateur (2026-10-21). Les deux crates sont supprimés du workspace, avec les cibles `make tui` et `make cli` et la règle A4 de `tools/check-architecture` (dépendances des clients CLI/TUI). La façade `Engine` et son contrat versionné ne changent pas.
- **Couverture** : les scénarios S1–S14 restent testés au niveau du moteur (`scenario_s*` de `mira-core/tests`). Disparaissent : l'invariant 6 (« chaque variante de `Request` a une commande CLI », sans objet sans CLI), les tests du CLI (codes de sortie, enveloppe `--json`, secrets par stdin) et les bancs de performance qui passaient par lui (`cli_support/*_bench`).
- **Écart à la référence** : la référence demande un moteur utilisable sans interface, en ligne de commande, pour tout tester sans écran (§ objectifs 6, D-04). Les tests automatiques de `mira-core` et du pont tiennent ce rôle ; proposition PR-19.
- **Retour arrière** : restaurer `engine/crates/mira-cli` et `engine/crates/mira-tui` depuis le commit précédant ce retrait, la ligne `mira-tui` des dépendances du workspace, la règle A4 et ses deux auto-tests.
