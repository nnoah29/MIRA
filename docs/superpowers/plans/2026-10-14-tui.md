# TUI de MIRA — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** Un client terminal complet pour MIRA (lecture et tri, rédaction, comptes et paramètres), posé sur la façade `Engine`, dans un crate à part `mira-tui`.

**Architecture :** Flux à sens unique : `state` (données pures) → `update(&mut AppState, Msg) -> Vec<Command>` (un handler par intention) → `view` (ratatui, sans effet de bord). Un pont asynchrone (`app/`) exécute les `Command` sur un `Arc<Engine>` dans des tâches `tokio`, et réinjecte réponses et événements du moteur sous forme de `Msg`.

**Tech Stack :** Rust 1.99.0 (édition 2024), `ratatui`, `crossterm`, `tokio`, `mira-assembly` (façade). Tests : `ratatui::backend::TestBackend`, testkit sur `127.0.0.1`.

**Spec :** `docs/superpowers/specs/2026-10-14-tui-design.md`

## Global Constraints

- Crate `engine/crates/mira-tui` (binaire `mira-tui`, bibliothèque `mira_tui`), branche `feat/E-01-tui`. `mira-cli` n'est pas modifié.
- Le TUI ne dépend **que** de `mira-assembly` parmi les crates `mira-*` en normal (jamais `mira-core` ni un provider, règle A4) ; dev-dépendances : `mira-testkit`, `tempfile`.
- Pas d'`unsafe`, pas d'`unwrap`/`expect`/`panic!`/`todo!` hors tests. Aucun secret affiché, journalisé, ni conservé dans l'état après l'envoi de la requête.
- Normes `tools/check-norms` : fonction ≤ 30 lignes ; fichier ≤ 6 fonctions avec corps (tests compris, tests dans `tests/`, un fichier par comportement) ; aucun commentaire dans un corps de fonction ; une seule ligne `///` en français avant chaque `fn` ; pas de `utils`/`helpers`/`common`/`misc` ; `match` exhaustif ; identifiants en anglais.
- Tests uniquement contre le testkit sur `127.0.0.1`, jamais de compte réel ; pas de navigateur ; pas de `#[ignore]`.
- Ne jamais modifier `docs/MIRA-architecture-reference.md` ni `docs/GIT_WORKFLOW.md`. Décisions ambiguës → `docs/DECISIONS-AGENT.md` (AG-35…, contexte / choix / raison / retour arrière).
- Environnement de compilation : `export RUSTUP_TOOLCHAIN=1.99.0 CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=2` ; commandes `cargo` lancées depuis `engine/` ; pas de `| head` derrière cargo.
- Commits : un par fonctionnalité, `feat(tui): …`, **sans trailer d'attribution** (consigne de l'utilisateur) ; `./ci.sh` vert avant chaque commit. Push seulement vers `origin` sur `feat/E-01-tui`.
- Nouvelles dépendances à ajouter dans `[workspace.dependencies]` : `ratatui`, `crossterm` (dernières versions compatibles avec `cargo deny` : licences MIT/Apache, `wildcards = "deny"`).

## Review Focus

Entrées ou conditions que la spec implique sans les nommer, les plus probables d'abord ; chacune a son test dans la tâche indiquée.

1. **Séquences d'échappement dans le courrier** (objet, expéditeur, corps contenant `\x1b[2J`, `\x07`, etc.) : neutralisées à l'affichage, jamais envoyées telles quelles au terminal (Tâche 5).
2. **Corps absent hors ligne** (`incompatible_state.body_unavailable_offline`) : message clair dans le lecteur, pas d'erreur fatale (Tâche 6).
3. **États vides** : aucun compte, compte sans boîte, boîte vide → écran d'accueil ou « aucun message », jamais de panique ni de sélection hors limites (Tâches 4, 5).
4. **Terminal minuscule** (0×0, 1 ligne, 10 colonnes) : rendu sans panique (Tâche 9).
5. **Double envoi** (`Ctrl+Entrée` deux fois, ou envoi relancé) : une seule `IdempotencyKey` par brouillon, un seul message envoyé (Tâche 11).
